# シェル構文解析基盤: 技術検証・設計メモ

Issue #4(シェル構文解析基盤の技術検証・実装)に対応して行った技術検証の結果と、
自前パーサ(`src/engine/shell/`)の設計方針をまとめる。関連: `docs/requirements.md` 3章3節・9章リスク項目1。

## 1. `bash-parser` の検証結果

要件定義書9章では「既存npmパッケージ(`bash-parser`等)がReact Native環境(Hermes)で動作するか」の
技術検証が求められている。今回の実装環境ではnpmレジストリへのネットワークアクセスが許可されておらず、
実機(Expo/Hermesランタイム)への `npm install` を伴う動作検証は実施できなかった。そのため、公開されている
`bash-parser` の設計・実行モデルに基づく机上調査で判断した。判断材料は以下の通り:

1. **実行環境への依存**: `bash-parser` はコマンド置換(`` $() ``)やファイル名展開(グロブ)を解決する際に、
   実際にシェルコマンドを実行する「実行コールバック」や、Node.jsの `fs`/`glob` に依存した展開処理を前提とした
   設計になっている。本アプリは「実LinuxやDockerには接続しない・仮想ファイルシステム(VFS)上でコマンドを
   シミュレートする」方針(要件定義書 Context節)であるため、実OSのファイルシステムやシェル実行を前提とする
   展開モデルとは根本的に噛み合わない。
2. **Node.jsコア依存**: 上記の展開処理は `fs` 等のNode.jsコアモジュールに依存する。Expo/Hermes環境には
   これらのモジュールは存在せず、Metroバンドラも解決できない。ポリフィルで塞ぐことは可能でも、意味的には
   「存在しない実ファイルシステムに対するダミー実装」になり、本質的な解決にならない。
3. **AST/実行モデルの不一致**: 本アプリが必要とするのは「構文解析(パース)のみ」であり、展開・実行は
   VFS上で動く自前のインタプリタ(別Issueで実装予定)が担う。`bash-parser` の出力ASTは実行コールバックの
   有無で構造が変わるなど、パースと実行が密結合した設計であり、パース専用の薄い利用は難しい。

以上より、**既存パッケージをベースにする第一候補は採用せず、要件定義書9章の代替方針どおり、必要な文法
サブセットに絞った自前パーサ(字句解析→AST)を実装する**方針とした。

> 補足: 上記はCI実行環境の制約により実機インストール検証ではなく設計調査に基づく判断である。将来
> ネットワークアクセス可能な環境で実際に `npm install bash-parser` してMetroバンドルを試す追加検証を
> 行うことも可能だが、上記1〜3の構造的な不一致(VFS前提のアプリ設計と噛み合わない実行モデル)は
> インストールの可否によらず解消しないため、方針への影響は小さいと考える。

## 2. 自前パーサの実装(`src/engine/shell/`)

- `lexer.ts`: 文字列 → トークン列(`tokenize`)。クォート・変数展開・コマンド置換・算術展開の境界を
  文字単位で走査して解決する。
- `parser.ts`: トークン列 → AST(`parseScript`)。再帰下降パーサ。`$(...)` の中身は文字列として
  一度切り出した後、`parseScript` を再帰呼び出しして子ASTを構築する。
- `ast.ts`: AST型定義一式(`Script` / `AndOrList` / `Pipeline` / `SimpleCommand` / `Word` / `WordPart` など)。
- `errors.ts`: `ShellSyntaxError`(構文エラー、発生位置を保持)。

React Native / Expo(Hermes)に依存しない純粋なTypeScriptとして実装しており(`src/README.md` の
`engine/` 方針に準拠)、正規表現も基本的な文字クラス(`[A-Za-z_]` 等)のみを使用しているため、Hermes上での
動作に懸念はない。

### 対応した構文(Issue #4のスコープ)

- 変数展開: `$name` / `${name}` / 位置パラメータ(`$0`〜`$9`) / 特殊パラメータ(`$?` `$#` `$@` `$*` `$$` `$!` `$-`)
- クォート: シングルクォート(`'...'`、無展開)・ダブルクォート(`"..."`、変数展開等は有効)
- コマンド置換: `$(...)` / `` `...` ``(ネスト・入れ子クォート対応)
- 算術展開: `$((...))`(式自体の評価はせず、生テキストとして保持)
- パイプ: `|`
- リダイレクト: `>` `>>` `<` `[n]>` `[n]>&m`(fd複製)
- コマンド区切り: `;` `&&` `||`
- コマンド先頭の変数代入: `NAME=value cmd ...`

### 意図的にスコープ外とした事項(今後のIssueで対応)

- 制御構造(if/for/case/while)・関数定義・バックグラウンド実行(`&`)・ヒアドキュメント(`<<`)・
  サブシェル(`(...)`) — Issue #4の「やること」に含まれないため未対応。遭遇時は `ShellSyntaxError` で
  明確に理由を示す。
- `${name:-default}` 等のパラメータ展開演算子・算術式(`$((...))`)自体の**評価**、単語分割(IFS)・
  グロブ展開の**適用** — パーサはこれらの構文的な境界を正しく切り出すところまでを責務とし、実際の
  展開・評価は今後実装するインタプリタ(採点エンジンと合わせて実装予定、要件定義書3章参照)の責務とする。

## 3. 使い方

```ts
import { parseScript, ShellSyntaxError } from "@engine/shell";

try {
  const script = parseScript('echo "hello $USER" | grep -i "$1" && echo ok');
  // script.commands: AndOrList[] ...
} catch (error) {
  if (error instanceof ShellSyntaxError) {
    // error.position に構文エラー発生位置(0始まり文字インデックス)
  }
}
```
