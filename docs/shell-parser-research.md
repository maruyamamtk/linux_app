# シェル構文解析基盤 技術検証・設計メモ

Issue #4 対応。`docs/requirements.md` 3章3節・9章リスク項目1 に関する検証結果と、
`src/engine/shell/` の設計方針をまとめる。

## 1. 既存パッケージ(`bash-parser`)の採用可否

要件定義書9章では「既存のbash構文パーサ(例: npm `bash-parser`)をベースにAST化する方式を第一候補とする」とされているが、以下の理由から**採用を見送り、自前パーサを実装する**方針とした。

### 検証内容と制約
本タスクの実行環境では `npm install`(package-lock.jsonに基づく依存解決)は許可されているが、
`npm view` や `npm install <未記載パッケージ>` のような任意パッケージに対するネットワークアクセスは
実行時の権限設定により許可されなかった(コマンドが承認待ちのまま完了しないため実行できない)。
そのため、`bash-parser` を実機インストールして Hermes/Expo 環境で動作確認する、という
最も確実な検証は今回も実施できていない。

### 設計上の不採用理由(実行確認とは独立した判断根拠)
仮に `bash-parser` がHermes上でパースエンジンとして動作したとしても、以下の理由で
本アプリの要件と根本的に相性が悪いと判断した。

1. **実行モデルの前提が「実OS上での実行」であること。**
   `bash-parser` は構文解析結果(AST)を提供するライブラリであり、コマンド置換 `$()` の
   値解決やグロブ展開・チルダ展開などの「展開」処理は呼び出し側が実装する必要がある。
   本アプリは実OS/実ファイルシステムを持たず、すべてVFS(仮想ファイルシステム)上で
   シミュレートするため、結局のところ「AST上のコマンド置換ノードをVFS実行結果で
   置き換える」独自の評価器を自前で書く必要があり、パーサ部分だけを外部化するメリットが薄い。
2. **保守されているとは言えない依存chainのリスク。**
   `bash-parser` は近年活発なメンテナンスがされておらず、React Native/Hermes環境での
   動作保証もされていない。バンドルサイズ・依存パッケージ数の観点でもモバイルアプリには
   重く、オフライン動作必須というアプリの非機能要件(要件定義書7章)とも噛み合わない。
3. **対応構文が要件よりも過不足している。**
   本アプリのPhase1で必要な構文(変数展開・クォート・コマンド置換・算術展開・パイプ・
   リダイレクト・`; && ||`)は限定的であり、汎用のbash全文法(関数・配列・複雑なパラメータ
   展開の全演算子・プロセス置換等)までは不要。自前実装であれば必要な範囲に絞れる分、
   コードサイズと学習コストを抑えられる。

以上より、**必要な文法サブセットに絞った自前パーサ(lexer→parser→AST)を実装する**方針を採用した。

## 2. 実装方針

### ディレクトリ構成
```
src/engine/shell/
├── ast.ts      # AST型定義
├── errors.ts   # ShellSyntaxError
├── lexer.ts    # 文字列 → トークン列(単語はクォート解除・展開まで解決)
├── parser.ts   # トークン列 → AST(再帰下降パーサ)
├── index.ts    # バレルエクスポート
├── lexer.test.ts
└── parser.test.ts
```

`src/engine/vfs/` と同様、React Native/Expoに依存しない純粋なTypeScriptとして実装している。

### 対応する構文
- 変数展開: `$var` `${var}` `${var:-default}` `${var:=default}` `${var:?message}` `${var:+alt}`、
  `${#var}`(長さ取得)、位置パラメータ(`$1`〜`$9`, `${10}`以降は波括弧が必要)、
  特殊パラメータ(`$?` `$#` `$@` `$*` `$$` `$!` `$-` `$0`)
- クォート: シングルクォート(展開なし)、ダブルクォート(変数展開・コマンド置換のみ解決、
  グロブ・単語分割はしない)
- コマンド置換: `$(cmd)` および `` `cmd` ``。ネスト可能で、中身は再帰的に本パーサで解析する
- 算術展開: `$((expr))`。式自体の評価(四則演算等)は実行系(採点エンジン)側の責務とし、
  パーサでは生テキストとして保持する
- パイプ: `|`
- リダイレクト: `>` `>>` `<`、および `[n]>&m` / `[n]<&m` 形式のfd複製(`2>&1` 等)
- 区切り: `;` `&&` `||` および改行
- コマンド先頭の変数代入(`FOO=bar cmd`, 代入のみの `FOO=bar` も可)

### スコープ外(意図的に未対応。遭遇時は `ShellSyntaxError` を投げる)
- 制御構造(`if/for/while/case`)・シェル関数定義・予約語(`{ }` によるグループコマンド含む)
- バックグラウンド実行 `&`
- ヒアドキュメント `<<` / ヒアストリング `<<<`
- サブシェル `( )`

これらはIssueのスコープ外であり、後続のIssueで制御構造・関数を実装する際に
本パーサ(lexer/parser/AST)を拡張する想定。未対応構文はサイレントに誤動作させず、
明示的な `ShellSyntaxError` を投げることで、上位層(コマンドインタプリタ)が
「未対応構文です」という形でユーザーにフィードバックできるようにしている。

### 設計判断メモ
- **lexerが展開まで解決する。** 実シェルの字句解析と同様、クォート境界を無視して
  `|` や `;` を演算子と判定することはできない(例: `"a|b"` はパイプではない)ため、
  lexerの単語スキャン処理内でクォート解除・変数展開・コマンド置換・算術展開まで
  解決し、`Word`/`WordPart[]` としてトークンに持たせている。
- **lexerとparserの相互参照。** コマンド置換 `$(...)` の中身をその場で再帰的に
  ASTへ変換するため、`lexer.ts` が `parser.ts` の `parseScript` を呼び出す
  (`parser.ts` も `lexer.ts` の `tokenize` を呼ぶため相互参照になるが、
  どちらも関数呼び出しの中でのみ使用しモジュール初期化時には参照しないため問題ない)。
- **IO番号の判定規則。** `2>file` のように数字列の直後に空白なしで `<`/`>` が
  続く場合のみ、その数字列をfd番号として扱う(`abc2>file` のように数字が
  他の文字と連続している場合は通常の単語として扱う、という実シェルの挙動を踏襲)。
- **代入の判定。** トークンの生テキスト(`raw`)が `^[A-Za-z_][A-Za-z0-9_]*=` に
  一致するかどうかで判定する。クォートされた `"FOO"=bar` は代入とみなさない
  (実シェルと同じ挙動)。判定は単純コマンドの先頭で非代入語が現れるまでの間のみ行う。
- **予約語の判定。** トークンの生テキストが予約語と完全一致する場合のみエラーにする
  (`echo if` のような引数位置や、`"if"` のようにクォートされた場合は誤検知しない)。

## 3. 未実行・要確認事項
- CI環境で `npm install` は成功し、`npm run typecheck` / `npm run lint` / `npm test` を
  実行して確認済み(全66件のテストがパス、lint/typecheckエラーなし)。
- `bash-parser` そのものを実機インストールしての動作検証は、本タスクの実行権限では
  依然として実施できていない。将来的に実施する場合は、`--allowedTools` にpackage.json未記載の
  npmパッケージに対する `npm install` / `npm view` を許可する必要がある(ただし上記2章の
  設計上の理由により、採用する可能性は低いと考えている)。
