# Vimシミュレータ 技術検証・設計メモ

Issue #47 対応。`docs/requirements.md` 3章5節(画面構成)・9章リスク項目3 に関する設計結果と、
今後 `src/engine/vim/` を実装する際の方針をまとめる。本ドキュメントは実装(コーディング)には
着手せず、着手前の詳細設計のみを行う(9章「Vim/Gitシミュレータの実装コスト」で個別の詳細設計を
挟むことが推奨されているため)。

## 1. 前提・スコープの確認

- 対象は書籍Ch7「vi(m)エディタ」。要件定義書2章のPhase2表では「ノーマル/インサートモード、
  dd/yy/p、`:%s/old/new/g`」が演習内容の例として挙がっている。
- 既存の仮想ターミナル(`src/ui/components/Terminal.tsx` + `src/engine/interpreter`)や
  シェル構文解析基盤(`docs/shell-parser-research.md`)とは独立したモジュールとして実装する。
  Vimはシェルのコマンドラインではなく専用のモーダルエディタであり、キー入力の解釈方式が
  シェルの字句解析(単語・演算子)とは根本的に異なるため、既存の `src/engine/shell/` は再利用しない。
- 一方で、`:%s/old/new/g` の置換文字列処理・アドレス範囲処理は `src/engine/commands/sed.ts` が
  既に持つロジック(BRE→JS RegExp変換、置換文字列内の `\1` `&` 変換、区切り文字読み取り)と
  ほぼ同一の問題であるため、可能な限り流用する(4.4節参照)。

## 2. 状態モデル設計

### 2.1 モード

ノーマル/インサートに加え、exコマンド(`:`)を入力するための「コマンドラインモード」を
独立したモードとして持たせる(`:%s/old/new/g` の入力自体がノーマルモードの1キー操作では
表現できないため)。

```ts
export type VimMode = "normal" | "insert" | "cmdline";
```

ビジュアルモード(`v` `V` `Ctrl-v`)は状態モデル上は別モードとして追加しうるが、今回はスコープ外とする(4章参照)。

### 2.2 バッファ(行配列)の表現

バッファは「改行を含まない文字列の配列」として表現する(単一の文字列 + 改行位置計算ではなく)。

```ts
export interface VimBuffer {
  /** 1行 = 配列の1要素。各要素は改行文字を含まない。空バッファは [""] (1行・空文字列)。 */
  lines: string[];
}
```

**採用理由:**
- Vimの操作の大半(`dd`/`yy`/`j`/`k`/`gg`/`G`/`:%s`のアドレス範囲)は「行」を単位とした操作であり、
  行配列であれば `lines.splice(...)` でそのまま実装できる。単一文字列 + インデックス管理だと、
  操作のたびに改行位置を再計算する必要があり複雑化する。
- `src/engine/commands/sed.ts` の `runSed` も内部で `text.split("\n")` して行配列に変換してから
  処理しており、同じ表現を採用することで `:%s` 実装時にsedの行処理ロジックをほぼそのまま移植できる。
- 演習の採点(6章)では最終的に `lines.join("\n") + "\n"`(末尾改行あり、VFSの一般的なテキスト
  ファイル表現)に戻して比較する。

### 2.3 カーソル位置

```ts
export interface CursorPosition {
  /** 0-indexed 行番号。 */
  line: number;
  /** 0-indexed 列番号(UTF-16コードユニット単位)。 */
  col: number;
}
```

- 列は「文字インデックス」ではなく `string` の添字(UTF-16コードユニット)で扱う。演習で使う
  ファイル内容は書籍のサンプル(設定ファイル・スクリプト等、ASCII中心)を想定しており、
  サロゲートペア(絵文字等)を含むテキストの編集は対象外とする。日本語(全角文字)はコメント等に
  含まれる可能性があるが、1コードユニット=1文字として扱って問題ない範囲に留める(要件定義書
  7章「日本語UIのみ」とは別軸の話であり、バッファの**中身**の日本語対応は将来課題とする)。
- ノーマルモードでは実際のvimと同様「行末の改行文字の位置にはカーソルが乗らない」制約
  (`col <= max(0, lines[line].length - 1)`)を課す。インサートモードのみ `col === lines[line].length`
  (行末)を許可する。

### 2.4 レジスタ(ヤンク/削除バッファ)

```ts
export interface VimRegister {
  content: string;
  /** true: 行単位(dd/yy等)。false: 文字単位(x/dw等)。pの貼り付け方が変わる。 */
  linewise: boolean;
}
```

- 無名レジスタ(`""`)のみを実装する。名前付きレジスタ(`"a`, `"b` 等)・システムクリップボード
  連携は対象外とする(4章)。

### 2.5 コマンド組み立て中の状態

Vimのノーマルモードのキー入力は「1キー1操作」ではなく `[count][operator][count]motion`
(例: `3dw`, `2dd`)のような複数キーの組み合わせで1つの操作になる。これをモバイルの
オンスクリーンキー入力でも同じ規則で組み立てられるよう、「入力中のキー列」を明示的に状態として持つ。

```ts
export interface PendingCommand {
  /** 操作全体の前置カウント。例: "3dd" の "3"。空文字列なら未指定(count=1として扱う)。 */
  count: string;
  /** 待機中のオペレータ("d" | "y" | "c")。未入力ならnull。 */
  operator: "d" | "y" | "c" | null;
  /** operator確定後に続けて入力された、モーション側のカウント。例: "d3w" の "3"。 */
  motionCount: string;
}
```

- `count` と `motionCount` は掛け合わせて実効回数とする(実vimと同じ: `2d3w` → 6語削除)。
- `g` 単独入力(`gg` の1打目)や `f`/`t`(文字検索、4章でスコープ外と判断)のような
  「次の1キーを引数として待つ」操作も同じ `PendingCommand` を介した小さな状態機械で表現する。

### 2.6 VimState 全体像

```ts
export interface VimState {
  mode: VimMode;
  buffer: VimBuffer;
  cursor: CursorPosition;
  register: VimRegister;
  pending: PendingCommand;
  /** コマンドラインモード("`:`"入力中)のバッファ。先頭の "`:`" は含まない。 */
  commandLine: string;
  /** 直前の ":" コマンド実行結果メッセージ(エラー時は赤字表示等、UI側で利用)。 */
  statusMessage: { text: string; isError: boolean } | null;
  /** undo用の直前バッファのスナップショット列(4.5節)。 */
  undoStack: VimBuffer[];
  redoStack: VimBuffer[];
  /** 画面要件(要件定義書5章)の「キー入力ログ」表示用に、これまでに入力された生キーを保持する。 */
  keyLog: string[];
}
```

`applyKey(state: VimState, key: VimKey): VimState` のような単一のリデューサ関数を
エントリポイントとして設計する(Reactの `useReducer` とそのまま対応させやすく、
`Terminal.tsx` が `executeShellInput` を呼ぶのと同様の構造にできる)。`VimKey` は
生の文字キー(`"d"`, `"$"`, `"Escape"`, `"Enter"` 等)を表す文字列の判別共用体とする。

## 3. モード遷移

| 現在のモード | 入力 | 遷移先 | 備考 |
|---|---|---|---|
| normal | `i` `a` `I` `A` `o` `O` | insert | カーソル位置・新規行挿入位置がキーごとに異なる(4.3節) |
| insert | `Escape` | normal | カーソルは1つ左に移動(実vimと同じ挙動) |
| normal | `:` | cmdline | `commandLine` を空文字列で初期化 |
| cmdline | `Enter` | normal | `commandLine` の内容をexコマンドとしてパース・実行(4.4節) |
| cmdline | `Escape` | normal | `commandLine` を破棄して何もしない |
| normal | `Escape` | normal | 何もしない(pendingをクリアするだけ)。既存の実vim挙動を踏襲 |

## 4. 対応するキー操作・exコマンドの範囲

書籍Ch7本文(要件定義書2章の演習内容欄: 「ノーマル/インサートモード、dd/yy/p、
`:%s/old/new/g`」)に沿って、以下の範囲を**対応スコープ**とする。

### 4.1 モーション(カーソル移動・オペレータの対象範囲指定の両方に使う)

| キー | 意味 |
|---|---|
| `h` `j` `k` `l` | 左/下/上/右へ1文字・1行 |
| `0` | 行頭(列0)へ |
| `$` | 行末へ |
| `w` | 次の単語の先頭へ |
| `b` | 前の単語の先頭へ |
| `e` | 単語の末尾へ |
| `gg` | バッファ先頭行へ |
| `G` | バッファ最終行へ(`{count}G` で指定行へ) |
| `{count}` + 上記 | 繰り返し回数 |

`f{char}`/`t{char}`(行内文字検索)、`{`/`}`(段落移動)、`%`(対応括弧移動)は
書籍Ch7の説明範囲を超えるため4.6節でスコープ外とする。

### 4.2 オペレータ + モーション

| キー | 意味 |
|---|---|
| `d` + モーション | 削除してレジスタへ(例: `dw`, `d$`, `dG`) |
| `dd` | 現在行を削除(行単位) |
| `y` + モーション | ヤンク(コピー) |
| `yy` | 現在行をヤンク(行単位) |
| `c` + モーション | 削除してインサートモードへ(例: `cw`) |
| `x` | カーソル位置の1文字を削除(`dl` の糖衣、レジスタにも入る) |
| `D` | `d$` の糖衣(カーソル位置から行末まで削除) |
| `Y` | `yy` の糖衣 |
| `p` | レジスタの内容をカーソルの後ろ(行単位なら次行)に貼り付け |
| `P` | レジスタの内容をカーソルの前(行単位なら前行)に貼り付け |
| `u` | undo |
| `Ctrl-r` | redo |
| `{count}` + 上記 | 繰り返し回数(例: `3dd`, `2p`) |

`c`/`d`/`y` は同一実装(「範囲を確定してから削除/ヤンク/削除+挿入モード」という
共通の内部関数に分岐を1つ足すだけ)にできるため、実装コストは3操作でも大きくは増えない見込み。

### 4.3 インサートモードへの入り方

| キー | カーソル/挿入開始位置 |
|---|---|
| `i` | カーソル位置の直前 |
| `a` | カーソル位置の直後 |
| `I` | 行頭 |
| `A` | 行末 |
| `o` | 現在行の下に新規行を作りその行頭 |
| `O` | 現在行の上に新規行を作りその行頭 |

挿入モード中の文字入力・`Backspace`・`Enter`(改行して行を分割)は通常の
テキスト編集として素直に `lines` を更新する(モバイルの `TextInput` からの入力イベントを
そのままこの経路に流す想定)。

### 4.4 exコマンド(`:` に続けて入力)

| コマンド | 意味 |
|---|---|
| `:{n}` | n行目へ移動 |
| `:s/old/new/` | カーソル行内の最初の `old` を `new` に置換 |
| `:s/old/new/g` | カーソル行内の全ての `old` を置換 |
| `:%s/old/new/g` | 全行が対象(`%` = `1,$`) |
| `:{n},{m}s/old/new/g` | n行目〜m行目が対象 |
| `:w` | 「上書き保存」相当(演習内では採点用にバッファ内容を確定させる合図として扱う。実際のVFS書き込みは6章参照) |
| `:q` | 演習を抜ける操作の合図(未保存警告等は行わない簡易実装) |
| `:wq` | `:w` + `:q` |

**実装方針:** `:s` / `:%s` のパース・置換処理は `src/engine/commands/sed.ts` の
`readUntilDelimiter` (区切り文字探索・エスケープ処理) と `translateReplacement`
(`\1` `&` `\&` `\\` → `String.replace` 用置換文字列変換) をそのまま流用する。
Vimのデフォルト正規表現(no-magicではない「magic」モード)は `(` `)` `{` `}` `+` `?` `|` に
バックスラッシュを要求する点でsedのBRE(基本正規表現)と一致するため、
`translateBreToJsRegExp` によるBRE→JS RegExp変換もそのまま使える。
アドレス部分(`%`, `{n},{m}`)は `sed.ts` の `SedAddress`/`SedRange` を単純化した
専用パーサ(行番号と `%` のみ。sedの `/regex/` アドレスや `$` は当面不要)を新設する。

### 4.5 undo/redo の実装方針

`u`/`Ctrl-r` は、操作(オペレータ・挿入モードの1回の入力確定・`:s`)のたびに
編集前の `VimBuffer` を `undoStack` に積み、`u` でpopして `redoStack` に積み直す
単純な「スナップショット方式」を採用する(実vimの差分ベースundoツリーのような
高度な機構は不要。1演習あたりの編集回数は多くても数十回程度であり、行配列の
コピーをその都度積んでもパフォーマンス上の問題にならない)。

### 4.6 対応キー一覧のまとめ

上記4.1〜4.4のキー・exコマンドが対応スコープの全てである。

## 5. スコープ外(意図的に未対応)

書籍Ch7・要件定義書の演習内容(dd/yy/p, `:%s/old/new/g`)を超える範囲は、
実装コストに対して学習効果が薄いため今回は対象外とする。未対応のキーが入力された場合は
サイレントに無視するのではなく、`statusMessage` に「未対応の操作です」的なメッセージを
表示し、`docs/shell-parser-research.md` のシェルパーサが `ShellSyntaxError` を投げる
方針と同様、ユーザーにフィードバックする。

- **ビジュアルモード** (`v` `V` `Ctrl-v`): オペレータ+モーションの組み合わせで
  dd/yy/p相当の操作は表現できるため、範囲選択の可視化までは今回実装しない。
- **マクロ** (`q{register}` 記録、`@{register}` 再生): 学習対象範囲を超える。
- **マーク** (`m{a-z}`, `` `{a-z} ``): 同上。
- **名前付きレジスタ** (`"a` 等)・システムクリップボード連携。
- **検索** (`/pattern`, `?pattern`, `n`, `N`): 独立した検索状態(検索方向・ハイライト・
  「見つからない場合」のメッセージ等)を新たに設計する必要がありコストが大きいため見送る。
  検索が必要な演習は `:%s/pattern/pattern/g`(置換先を同じ文字列にする)等で代替できる範囲に留める。
- **文字単位モーションの一部** (`f{char}` `t{char}` `F{char}` `T{char}` `%` `{` `}`):
  4.1節参照。
- **置換モード** (`R`)、**単一文字置換** (`r{char}`): 学習効果に対してコスト(実装+UI)が
  見合わないため見送る。同等の結果は `x` + インサートモードで得られる。
- **ウィンドウ分割・タブ・バッファ切り替え**: 本アプリは1演習=1バッファのため概念自体が不要。
- **`.`(直前操作のリピート)**、**`~`(大文字小文字反転)**: 対象外。
- **`:g/pattern/d` 等のグローバルコマンド**: `sed.ts` にも未実装であり、今回のVim側でも見送る。

## 6. 採点(グレーディング)方針への反映

既存の採点エンジン(`src/engine/grading`)は「ユーザー入力と模範解答をそれぞれ同一環境で
実行し、観測可能な効果を比較する」方針(要件定義書3章5節・9章2)を採っている。Vim演習も
同じ方針を踏襲する:

- `Exercise` 型(`src/content/exercises.ts`)に `type: "vim"` を追加し、既存の
  `referenceSolution` フィールドを「模範解答のキー入力列」(例: `"ggdd"`, `":%s/old/new/g\n"`)
  として再利用する。ユーザー側も、実際に押されたキー列(`VimState.keyLog` 相当)ではなく、
  同じ初期バッファに対してユーザーのキー入力列を再生した**最終的なバッファ内容**を、
  模範解答のキー入力列を再生した最終的なバッファ内容と突き合わせる。
- これにより、同じ結果に到達する別解(例: `dd` vs `:1d` 相当のキー列)を許容できる
  (要件定義書3章5節の採点エンジンの設計方針と一貫性を保てる)。
- 比較対象は「バッファの最終テキスト内容」を第一候補とする。カーソル位置・undoスタックの
  比較は行わない(学習者に見えない内部状態であり、正誤判定に含めると別解を不当に不正解に
  してしまうため)。

## 7. 画面構成への反映

要件定義書3章5節の「Vim演習画面(Phase2): モード表示・キー入力ログ・現在のバッファ内容」は、
本設計の `VimState` にそのまま対応する:

- モード表示 → `VimState.mode`(+ `pending` の内容を「入力中: `2d`」のように補助表示すると
  操作の途中経過が分かりやすい)
- キー入力ログ → `VimState.keyLog`
- 現在のバッファ内容 → `VimState.buffer.lines`(+ `VimState.cursor` をカーソル位置のハイライトに使う)
- コマンドラインモードの入力中テキスト・実行結果メッセージ → `VimState.commandLine` / `statusMessage`

物理キーボードの `hjkl` 等を前提にできないモバイル環境向けに、画面下部にVim操作用の
専用キーパッド(モード別のボタン列)を配置し、そこからのタップイベントを `VimKey` として
`applyKey` に流し込む方式を想定する。この専用キーパッドの詳細UI(ボタン配置・レイアウト)は
画面実装フェーズで別途詰める(本ドキュメントは状態モデルとキー操作範囲の設計が主眼のため)。

## 8. 実装ディレクトリ構成(案)

`src/engine/shell/` や `src/engine/vfs/` と同様、React Native/Expoに依存しない
純粋なTypeScriptモジュールとして実装する想定。

```
src/engine/vim/
├── types.ts        # VimState/VimMode/VimBuffer/CursorPosition/VimRegister/PendingCommand 等
├── state.ts         # createInitialState, applyKey(state, key) のエントリポイント
├── motions.ts        # h/j/k/l/w/b/e/0/$/gg/G の移動先計算
├── operators.ts      # d/y/c + モーション、dd/yy/x/D/Y/p/P、undo/redo
├── exCommands.ts     # ":"以降のパース・実行(:s, :%s, :w, :q, :{n})。sed.tsのロジックを一部流用
├── errors.ts         # VimUnsupportedKeyError 等
├── index.ts          # バレルエクスポート
└── *.test.ts          # 各モジュール対応のユニットテスト
```

## 9. 未確定事項・今後の検証

  実装フェーズでプロトタイピングしながら決める(操作性に関わるため、コード設計だけでは
  決めきれない)。
- **`Exercise` 型・採点エンジンへの `type: "vim"` 追加の詳細**: 6章は方針レベルの設計であり、
  `gradeExercise` 側の具体的なシグネチャ変更は実装Issueで詳細化する。
- **日本語(全角文字)を含むバッファ内容編集時の列計算**: 2.3節の通り当面はUTF-16コードユニット
  単位で扱う前提とし、全角文字を含む演習を用意する場合は改めて検証する。
